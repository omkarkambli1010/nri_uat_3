 IMPORTANT - DO NOT INSTALL ESLINT 10
 ------------------------------------
 eslint-config-next@16.3.0 declares peer "eslint": ">=9.0.0", but its bundled
 eslint-plugin-react still calls context.getFilename(), which ESLint 10
 removed. Installing eslint@latest (10.x) makes "npm run lint" crash with:

     TypeError: Error while loading rule 'react/display-name':
     contextOrFilename.getFilename is not a function

 ESLint must stay pinned at ^9 until eslint-config-next ships a fix.

================================================================================
 STEP 3 - CODE / CONFIG CHANGES (file edits, not commands)
================================================================================

 These were applied by hand. Listed here so the reason for each is on record.

 3a. next.config.ts  -- added "turbopack: {}"
     Next 16 builds with Turbopack by default. A next.config.ts containing a
     "webpack" key with no "turbopack" key is now a HARD BUILD ERROR:

         ERROR: This build is using Turbopack, with a `webpack` config and
         no `turbopack` config.

     The existing webpack block only stubbed Node builtins
     (fs/net/tls -> false) for the browser bundle. Turbopack does not polyfill
     Node builtins into client bundles at all, so that stubbing is unnecessary.
     The webpack block was LEFT IN PLACE so that "next build --webpack"
     remains a working escape hatch if a Turbopack issue shows up.

 3b. package.json  -- "lint": "next lint"  ->  "lint": "eslint ."
     Next 16 removed the "next lint" command entirely.

 3c. eslint.config.mjs  -- NEW FILE (flat config)
     There was NO ESLint config in this repo at all, which means "next lint"
     never actually ran. Adding the config surfaced 434 pre-existing findings.
     None were caused by this upgrade. They are set to "warn" so that
     "npm run lint" exits 0 and is usable as a gate for NEW problems.
     Promote each rule back to "error" as its backlog is cleared.

 3d. SEO files -- see the SEO section further down.

 NOTE: Next also auto-reformatted tsconfig.json on first build and set
 "jsx": "react-jsx" plus added ".next/dev/types/**/*.ts" to "include".
 This is expected and required by Next 16.

================================================================================
 SEO / CRAWLER ENABLEMENT - WHAT CHANGED AND WHY
================================================================================

 GOAL: let Googlebot and other crawlers index the public pages, while keeping
 the KYC onboarding funnel out of the search index.

 WHY NOT INDEX EVERYTHING
 ------------------------
 The root layout previously set robots: "index, follow", and because it is the
 ROOT layout that applied to every route - including /uploadPan, /CaptureSelfie,
 /passportUpload, /manual-bankdetails, /esign, /personalDetailsForm and
 /nriapi. Those pages are thin, near-duplicate, session-scoped funnel steps.
 Indexing them dilutes ranking for the pages that matter and exposes the
 funnel structure. Only /home and /faq carry real search value.

 FILES ADDED
 -----------
     src/lib/seo.ts        Central SEO policy: site URL, public route list,
                           canonical URL helper, environment gate.
     src/app/robots.ts     Generates /robots.txt
     src/app/sitemap.ts    Generates /sitemap.xml

 FILES MODIFIED
 --------------
     src/app/layout.tsx    Default changed to noindex/nofollow + metadataBase
     src/app/home/page.tsx Opts INTO indexing + canonical + OpenGraph
     src/app/faq/page.tsx  Opts INTO indexing + canonical + description

 NO COMPONENT FILES WERE MODIFIED.

 DESIGN DECISION 1 - DENY BY DEFAULT
 -----------------------------------
 The root layout now defaults every route to noindex, and /home and /faq opt
 back in individually. This means a NEW funnel step added later is protected
 automatically instead of silently becoming crawlable.

 DESIGN DECISION 2 - UAT IS NEVER INDEXED
 ----------------------------------------
 udn.sbisecurities.in serves the same pages as production. If it were indexed
 it would compete with production for the same queries. Indexing is therefore
 gated on NEXT_PUBLIC_ENV=production. On UAT, robots.txt blocks everything and
 the sitemap is empty.

 DESIGN DECISION 3 - THE DISALLOW IS SCOPED TO /diynri/, NOT /
 -------------------------------------------------------------
 robots.txt is served from the HOST ROOT, and other apps share this host -
 the commented-out config in src/environments/environment.ts shows
 /open-demat-account/ also lives on diy.sbisecurities.in. A bare
 "Disallow: /" would have deindexed that app too. The rule is scoped to the
 basePath instead. robots.txt uses longest-match-wins, so the two Allow lines
 correctly override the broader Disallow.

 VERIFIED OUTPUT - PRODUCTION
 ----------------------------
     User-Agent: *
     Allow: /diynri/home
     Allow: /diynri/faq
     Disallow: /diynri/

     Host: https://diy.sbisecurities.in
     Sitemap: https://diy.sbisecurities.in/diynri/sitemap.xml

     /home     -> <meta name="robots" content="index, follow">
                  <link rel="canonical" href=".../diynri/home">
     /faq      -> <meta name="robots" content="index, follow">
                  <link rel="canonical" href=".../diynri/faq">
     /uploadPan-> <meta name="robots" content="noindex, nofollow">
     /esign    -> <meta name="robots" content="noindex, nofollow">

 VERIFIED OUTPUT - UAT
 ---------------------
     User-Agent: *
     Disallow: /diynri/

     sitemap.xml is empty, /home is noindex,nofollow.

 Inspect the generated files yourself after a build:

     type .next\server\app\robots.txt.body
     type .next\server\app\sitemap.xml.body

 IMPORTANT - basePath AND robots.txt REACHABILITY
 ------------------------------------------------
 The app runs under basePath "/diynri", so Next emits these at
 /diynri/robots.txt and /diynri/sitemap.xml. Crawlers ONLY read
 <origin>/robots.txt. The existing "beforeFiles" rewrite in next.config.ts
 maps root-level .txt/.xml requests into /diynri/..., so both resolve
 correctly. DO NOT REMOVE THAT REWRITE or robots.txt becomes unreachable.

 After deploying to production, confirm from outside:

     curl https://diy.sbisecurities.in/robots.txt
     curl https://diy.sbisecurities.in/sitemap.xml

 Then submit the sitemap in Google Search Console:
     https://diy.sbisecurities.in/diynri/sitemap.xml
